# 2026-10-05 0=无上限/微博卡死/限流失效/断点续获取 + 下载中心浮窗空白修复

## 用户反馈（P1）

1. 条数填 0（无上限）时日志显示「访客仅 12 条（不足 9999）」——9999 是假无上限
2. 微博获取勾选自动下载后「一直不动」（深翻页无任何进度反馈，看起来像卡死）
3. 限流设置（每 N 个停 M 秒）只对抖音生效，微博/B站深翻页完全不停顿 → 容易被 ban
4. 无法断点续获取和下载（中途取消/崩溃，已完成账号的数据也一起丢）
5. 自动下载时下载进度全部堆在左侧日志，右侧「下载中心」浮窗批次卡片内容区空白

## 修复内容

### 1. 0 = 真无上限（info_accounts.py）

`fetch_count = count if count > 0 else 99999999999999`（原 9999）。
各平台以 `count >= 10**12` 识别为「无上限」：
- 抖音 HTTP 直调：50 页护栏 → 2500 页（has_more=False 自然停）
- 抖音 Playwright：5 轮滚动 → 400 轮（+停滞检测：连续 3 轮无新数据提前收尾）
- 快手浏览器：14/40 轮 → 2000 轮（同样停滞检测）
- 微博/B站：本就翻到断页为止，无上限显示进日志（「目标 无上限」）

### 2. 全平台翻页进度日志（防「一直不动」观感）

微博/B站视频/B站动态/抖音HTTP/抖音Playwright/快手：每 5 页（或 10 轮）打一条
`[平台] 已翻 N 页 · 累计 X 条（目标 Y/无上限），继续...`——深翻页几百页不再静默。

### 3. 限流停顿接入全部平台（原仅抖音）

微博 `_try_api_fetch` / B站 `_fetch_user_videos_once` / B站 `_fetch_dynamics_once`
新增 `pause_every/pause_secs` 参数（与抖音同语义：每抓 pause_every 条停
pause_secs 秒，按上一页实际条数折算）。info_accounts `_fetch_one` 对
douyin/weibo/bilibili 三平台统一传入限流设置（快手浏览器滚动自带 1.5s 节奏、
小红书首批 SSR 无翻页，不接）。

### 4. 取消可打断深翻页 + 断点保留（stop_check）

四平台 `fetch_user_posts` 新增 `stop_check` 回调：翻页/滚动循环每轮检查，
取消信号到达即停止并**保留已获取部分**（日志明示「保留已获取 N 条」）。
info_accounts 传 `stop_check=cancel_event.is_set`。

### 5. 逐账号即时入库/导出（断点续获取的核心）

原流程：全部账号采完 → 一次性导出（中途取消/崩溃 = 全丢，只有「已获取」
内存表）。
现流程：`_fetch_one` 完成一个账号 → 立即 `_export_one_batch`（增量入库或
单独导出，日志逐账号显示「💾 已入库 bilibili +150」）→ 收尾只打汇总行。
中途取消/崩溃只丢在飞账号，已完成账号的数据都已在库。增量模式按去重键
幂等，重跑不重复；单独导出模式 skip_existing，重跑只补新文件。
（下载侧的断点续下载本就由 skip_existing + 视频ID校验承载，配合逐账号
入库后重新获取→自动下载即增量下载。）

### 6. 下载中心浮窗批次卡片空白（download_panel.py）

**现象**：自动下载批次卡片只有标题行，面板内容区完全空白；下载进度全在
左侧日志。其他页面（单独解析/批量导入/资产页）的下载面板正常。

**根因**（真实平台探针实锤）：`_clear_layout` 对复用控件执行 `w.hide()`，
`_build_ui` 把它们重新 `addWidget` 回来**但不 show()**——Qt 的显式 hide
标记不因重新加入布局复位。
触发路径：`add_batch` 里 `card.plan()` 预渲染一次（正常），随后下载函数
（do_bilibili_download / download_media）自己的 plan 事件到达 → 第二次
`_build_ui` → batch_head/scroll 被-hide-未复show → **永久不可见**。
其他页面 `_build_ui` 只执行一次（面板从隐藏态首次构建），从不触发。

**修复**：`_build_ui` 与 `_build_placeholder` 中，复用控件重新入局后显式
`w.show()`（segments 模式 3 个、批量模式 2 个、placeholder 1 个）。

**验证**：真实 Windows 平台（有头）复现脚本——修复前 `scroll/batch_head/
row isVisible=False`，修复后全 True，grab 截图 8 槽位行完整渲染。

  第2次调用停止 → 保留 12 条断点 ✓
- B站 count=155：当日游客态被风控（API错误：风控校验失败）→ 自动回退

## 教训

- **「隐藏→重新加回布局」不等于恢复显示**：Qt 显式 hide 标记跨 setParent/
  addWidget 存活，复用控件重建 UI 后必须显式 show。单次构建的场景测不出
  这类 bug——**同一构建函数被第二个入口二次调用时才会引爆**
- 0=无上限的语义要贯穿全链路：UI 层偷换成小数字（9999）会让「翻到底」
  变成「翻到 9999」，护栏（50 页/14 轮）也要跟着分档
- 深翻页必须打进度日志：用户无法区分「慢」和「死」
- 限流参数加在新平台时，要排查所有调用点把 kwargs 传全（本次 weibo/bili
  签名加参 + info_accounts kwargs 分平台下发）
- offscreen 平台 isVisible/rendering 与真实 Windows 不一致，浮窗类 bug
  必须有头真窗口验证
