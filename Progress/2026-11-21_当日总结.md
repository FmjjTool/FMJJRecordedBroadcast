### 方案

## 115 下载「直链失效」修复（CDN 403）

### 现象与定位

- 用户实测下载 34.9 MB FLAC：日志连续 3 次「直链失效，重新申请」，最终失败。
- 该文案只来自下载引擎 `_LinkExpired`，即 `_stream()` 对直链发起 GET 后收到 **HTTP 401/403**；取链接口本身是通的（文件已列出、pickcode 正常），所以问题在 115 的下载 CDN，不在列目录。
- 与公开资料一致：115 从 2025-12 起对直链加了防盗链（Referer / UA / IP），有效期压到分钟级；网页端能下是因为它带着浏览器上下文，而我们的请求多了 `Origin`、UA 是普通 Chrome。

### 修复方案（`src/toolbox/drive115/api.py`）

| 改动 | 原因 |
| --- | --- |
| 会话头去掉 `Origin`，只保留 `Referer: https://115.com/` | CDN 把带 Origin 的 GET 当跨域请求处理并 403；网页的下载导航请求本身不带 Origin |
| 新增 `_probe_link()`：取链后用真实下载头 + `Range: bytes=0-0` 探活 | 在下载引擎之前暴露 CDN 的真实拒绝原因，不再只剩「直链失效」 |
| 探活 401/403 → 换 `115Browser/27.0.3.7` UA **重新申请**直链再探 | 直链与 UA 绑定，只换下载头没用，必须申请 + 下载同一 UA |
| 两种 UA 都失败 → 抛带 `HTTP 状态码 + 响应片段` 的错误，并在缺 `KID` 时点名 | 让下一次实测能直接看到 CDN 的理由（签名 / 防盗链 / 登录态），而不是盲猜 |
| `has_kid` 记录 Cookie 是否含 `KID` | 115 下载依赖 KID；若登录时没拿到，需要重新登录一次 |

### 第二轮：改为四组合探活 + 真因直接上报

### 第三轮：`no cookie value` 真因与「会话罐」改法

- 用户再次实测，四组合全部返回 `HTTP 403 {"message":"no cookie value"}`，主机 `cdnfhnfile.115.com`。
- 检索到 AList 115 驱动的同款故障记录：CDN 在下载请求上要求账号 Cookie，而 SDK 返回的下载头里不含 Cookie，日志同样是 `no cookie value`；补上 Cookie 即恢复。
- 我们的差异点：账号 Cookie 是写进 `session.headers["Cookie"]` 的**显式头**。requests 中显式 Cookie 头会**覆盖会话罐**，于是取链接口通过 `Set-Cookie` 下发的新 Cookie（CDN 可能正是靠它鉴权）被丢掉；同时 UA/Cookie 绑定的直链也会因头部来源单一而被判「没带 cookie」。
- 改法：
  - 账号 Cookie 解析成 dict 灌进 `session.cookies`，`session.headers` 不再写 `Cookie`（实测空域 Cookie 会发给 webapi 与 CDN 两个域名）。
  - 下载头默认不带 Cookie，让 requests 用会话罐（账号 Cookie + 取链时新下的 Cookie）；只有 `/files/download` 明确下发 `cookie` 字段时才显式带那一份。
  - 探活顺序简化为「会话罐 → 响应下发 cookie → 换 `115Browser` UA 重新申请后再试」；全败时错误里增加「取链响应字段」「会话罐新增 Cookie 数」，用于判断是否该转 `proapi` 加密取链。

### 第四轮：115 上传接入（秒传 + 阿里云 OSS 直传）

- 用户确认下载已跑通（2% / 102.3 KB/s，非会员限速），要求补上传。

  1. `POST proapi.115.com/app/uploadinfo` → `user_id` + `userkey`；
  2. `POST uplb.115.com/4.0/initupload.php?k_ec=<Token>`，**请求体 EC115 加密**：
     P-224 ECDH（远端公钥 56 字节固定）→ 共享密钥前 16 字节作 AES key、后 16 字节作 IV →
     PKCS7 + CBC；响应同一把 key/IV 解密后再解 LZ4 block（前 2 字节是小端长度）；
  3. 表单：`appid=0`、`appversion=27.0.5.7`、`userid`、`filename`、`filesize`、

     `t`（毫秒）、`token`；`sig = SHA1(userkey + SHA1(userid+fileid+target+"0") + "000000")` 大写；
     `token = MD5("Qclm8MGWUv59TnrR0XPg" + fileid + filesize + signKey + signVal + userid + t + MD5(userid) + appVer)`；
  4. `status=2` 秒传成功；`status=7` 需要二次校验（`sign_key` + `sign_val=SHA1(sign_check 区间)`）后重试一次；
     否则用返回的 `bucket / object / callback` 直传 OSS；
  5. OSS：`GET uplb.115.com/3.0/gettoken.php` 取临时凭证 → `PUT https://{bucket}.cn-shenzhen.oss.aliyuncs.com/{object}`，

## 下拉框/页签不再响应滚轮（滚轮只滚页面）

用户指出上一轮理解错了需求：要的不是「点得快点得动」，而是**下拉框根本不该随滚轮改选项**（鼠标停在「采集类型」上滚一下就悄悄变值）。

### 根因

`ui-visual-spec` 5.6 早写了「数字框、滑条、页签同样适用，统一在应用级事件过滤器里拦，控件声明 `wheelOk=true` 才放行」，但**这个应用级过滤器从未实现**：`QComboBox` 默认 WheelFocus，滚轮直接改值；`QTabBar` 也会淡滚切页签。此前只有 `pages/cover_maker.py` 自带一个 `NoWheelMixin` 局部规避。

### 改动

| 位置 | 改动 |
| --- | --- |
| `src/gui_qt/wheel_guard.py`（新增） | 应用级事件过滤器：`QComboBox` / `QTabBar` / `QSlider` / `QAbstractSpinBox` 收到滚轮时，把事件换算到最近 `QAbstractScrollArea` 视口后转发（页面照常滚动），并吞掉原始事件；`wheelOk=true` 放行；`QScrollBar` 不在名单（否则页面滚不动） |
| `src/gui_qt/__init__.py` | 包导入时尝试安装（QApplication 尚未创建则静默跳过） |
| `main.py` | QApplication + 主题就绪后显式 `wheel_guard.install()` |
| `src/skills/ui-visual-spec/SKILL.md` | 5.6 滚轮行补实现位置与 `QScrollBar` 例外 |

### 验证

| 项 | 结果 |
| --- | --- |
| 下拉框 | 滚动区内 `QComboBox` 滚轮：currentIndex 0→0（不变），滚动区 0→60（页面滚了） |
| 页签 | 滚轮后 currentIndex 仍为 0（不切页签） |
| 数字框/滑条 | `QSpinBox` 50→50、`QSlider` 50→50，滚动区继续滚到 120 |
| 放行通道 | `setProperty("wheelOk", True)` 的下拉框仍按滚轮改值 |
| 语法 | `python -m compileall -q src` 通过 |

### 未验证

- 未在真机滚一遍各页面（离屏可验证事件行为，真实滚轮手感需实机确认）；数字框/滑条改成只认拖动后，若某页确实需要滚轮调值，标 `wheelOk` 即可。
