# 2026-11-22 本地资料站「拉取代码」：通道走全 + 以云端为准

## 需求

用户截图「拉取代码」对话框报 `merge webwiki-api 失败（退出码 128）：fatal: refusing to merge unrelated histories`，质疑「有网络为什么拉取不了，我需要他尝试所有通道」，随后补充「仓库默认都是使用云端的」。

## 根因

1. **不是网络问题**：fetch 已经成功，失败发生在随后的本地 `merge --ff-only`。`download/本地资料站/webwiki-api` 是浅克隆，`.git/shallow` 里同时有本地 HEAD（`4c0c201`）与 FETCH_HEAD（`9c8d501`）两个边界，两者没有共同祖先（远端历史被重写 / 仓库重建），git 直接以 128 拒绝合并。
2. **通道也确实没走全**：旧实现只有「系统代理 → 直连」两档，系统代理读注册表（本机 `ProxyEnable=0`、`ProxyServer` 残留 `http://127.0.0.1:12450`），约定 15 里的本机常见端口 `7890 / 10809 / 12450` 与 `git config http.proxy` 都没进候选。
3. 旧逻辑还要求「确认没有本地提交」才敢对齐远端，只要本地有提交就停在报错；而本项目仓库以云端为准，本地提交不该阻塞拉取。

## 改动

| 文件 | 改动 |
| --- | --- |
| `src/toolbox/webwiki/config.py` | `proxy_candidates()` 按约定 15 重排：直连 → `WEBWIKI_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` → 系统代理 → 本机常见端口（HTTP + SOCKS5，先探活、同端口只探一次）→ `git config http.proxy`；新增 `normalize_proxy()`、`proxy_alive()`、`git_config_proxy()` |
| `src/toolbox/webwiki/gitops.py` | 通道逐档记录并在日志里提示换档；加 `GIT_HTTP_LOW_SPEED_LIMIT/TIME` 防止卡死；`_history_rewritten()` 抽成纯函数；远端历史重写时不再因「本地有提交」停下——建 `pre-sync-<时间>` 备份分支后 `reset --hard FETCH_HEAD`，仓库以云端为准；`pull_all()` 两个仓库互不阻塞、汇总报错 |
| `src/toolbox/webwiki/runner.py` | `capture(merge_stderr=False)` 丢弃 stderr，git 的 safe.directory / ignore 告警不再混进 porcelain 被误判成「有本地改动」 |
| `tests/test_webwiki_gitops_channels.py` | 新增 4 项通道阶梯/端口探活/历史重写判定单测，1 项真实 git 集成（本地 `file://` 远端重写历史 → 对齐云端并保留备份分支） |

## 验证

- `py_compile` 通过；4 项单测通过（`ProxyChannelTest` 3 项 + `test_rewrite_tail_detection`）。
- 集成用例逻辑用等价脚本实跑通过：浅克隆 + 本地自有提交 + 远端改写成另一棵树 → `_advance` 后 HEAD 对齐远端新提交、`pre-sync-*` 指向本地旧提交、工作区干净。沙箱内禁止程序化删除，`TemporaryDirectory()` 清理被拦，该用例只在本机（非沙箱）可跑。
- 在 `webwiki-api` 副本上复现原报错（`merge --ff-only` → 128 `refusing to merge unrelated histories`），按新逻辑 `reset` 到 `9c8d501`、备份分支保留 `4c0c201`。
- 真实桌面执行 `pull_all`：直连 21s 超时 / 连接被重置，本地代理端口 7890/10809/12450 均未监听，故本次未能代用户完成拉取；两个仓库内容未被改动。

## 推送记录（2026-11-22）

- 逐通道尝试推送：直连 → `Recv failure: Connection was reset`；`git config http.proxy`（仓库里残留 `socks5h://127.0.0.1:12450`，该端口未监听）→ 连接被拒；`IP 20.205.243.166 + Host: github.com` → 成功 `726682d..095e4e4`。
- 已按约定 15 清掉仓库级 `http.proxy` / `https.proxy`（均为失效的 `socks5h://127.0.0.1:12450`）；清掉后直连 github.com:443 仍然 21s 超时，说明本机到 github.com 的直连时通时断，IP + Host 头是当前可用通道。
- 远端 `refs/heads/main` 已确认等于本地 `095e4e4`。

## 一键部署：进度条 + 失败自动重新部署

**需求**：用户发「部署与启动」卡片截图，要求部署过程加进度条，并且这些步骤失败时直接重新部署。

**改动**：`src/gui_qt/pages/localwiki.py`

- 一键部署拆成 5 步（拉取代码 → 安装依赖 → 重建站点数据 → 构建前端 → 启动服务），每步开头回调主线程更新进度条：`第几步/共几步 + 当前动作`（如 `3/5 重建站点数据`）。
- 部署按钮下新增 `QProgressBar`（`wikiProgress`，palette 取色）与「取消」按钮：取消在当前步骤结束后生效，状态写「已取消（完成 N/5 步）」，已完成部分保留，不弹失败窗。
- 任一步异常 → 记日志「部署中断：原因」，整链从头重来一次（`DEPLOY_RETRIES = 1`）；两次都失败才抛「部署失败：已自动重新部署 1 次仍未成功（原因）。请查看下方日志里中断的那一步再重试。」
- `_start_task` 新增 `on_error` 回调：取消走静默分支，真正的失败仍走弹窗 + toast。
- 进度条完成后 3 秒自动隐藏；部署期间按钮禁用（沿用 `_refresh_actions`）。

**同步文档**：`src/skills/software-feature-guide/SKILL.md`「资料站」补 5 步流程、进度条与取消、失败自动重新部署、通道阶梯。

**验证**：

- 新增 `tests/test_localwiki_deploy_progress.py` 6 项（进度条文案/百分比、5 步顺序与两个仓库的拉取顺序、失败后整链重跑、两次失败的上报文案、取消停在当前步且不重试、取消不弹窗），offscreen 全部通过。
- 沙箱禁止程序化删除，`TemporaryDirectory` 清理会被拦，测试在沙箱内用等价的临时目录脚本跑通；未做真机 GUI 复核（运行中的实例按 running-instance-guard 不重启，需用户重启后看一眼进度条）。
