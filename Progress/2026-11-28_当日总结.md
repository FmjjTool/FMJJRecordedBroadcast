### 网络排查过程（按约定 15 逐档推进）

- 第一档直连（显式清空代理）：`Failed to connect to github.com:443 after 21065 ms: Could not connect to server`，在沙箱与宿主 PowerShell 两个通道均复现。
- 第二档代理回退：环境注入的 `127.0.0.1:39324` 返回 `CONNECT tunnel failed, response 502`；约定列出的常见端口 7890 / 10809 / 12450 全部不通。实际检查发现本机 Clash Verge（`verge-mihomo.exe`）监听的是 **7897**，且该端口访问国内站点返回 200，说明代理进程本身正常；但经它访问 GitHub 时 schannel 与 openssl 两种 TLS 后端分别在握手阶段失败（`failed to receive handshake` / `unexpected eof while reading`）。用户在排查中途告知代理已恢复，重新测试直连与 7897 仍为超时与 TLS 握手失败。

### 转发器调试与最终结果

- 首版两个缺陷已修复：一是 CONNECT 头与紧随其后的 TLS ClientHello 常在同一个包里，原实现会把后续数据丢弃；二是上游连接沿用了 20 秒超时，导致大 pack 上传期间空闲即被切断（表现为 `Proxy CONNECT aborted`）。另补充候选 IP 自动重试与健康 IP 记忆，应对 GitHub 各 IP 间歇性可达（日志可见 `140.82.113.3` 超时后自动切到下一个可用 IP）。

## 腾讯文档完整歌曲表读取失败

### 需求、根因与修复

- 用户反馈「完整歌曲」表无法查看。截图显示表格读取错误为 `[Errno 22] Invalid argument`，表格主体为空且仍显示上一张表的表头。
- 根因定位在 Windows 日期排序：公共日期解析器将不带年份的时间按 1900 年解析；对 1900 年及部分 1970 年前日期调用 `datetime.timestamp()` 会在 Windows 抛出 `OSError: [Errno 22] Invalid argument`。腾讯文档预览在推断日期列和排序时调用该路径，异常导致整页读取失败；残留旧表头是读取失败后的界面表现。由于按腾讯文档范围约束未接入真实完整歌曲数据，不能确认实际触发异常的具体单元格。
- `src/toolbox/table_sort_keys.py` 将同一日期解析器以 `parse_datetime` 名称公开，原通用 `sort_key()` 的排序行为不变；`src/toolbox/tcdoc/table_preview.py` 仅在腾讯文档预览的日期比较中直接比较解析后的 `datetime`。桌面和 WebUI 共用此预览实现。数字、日期、文本及空值类别保持不变，空值继续排在末尾。
- `src/skills/software-feature-guide/SKILL.md` 补充日期兼容范围。页面能力、业务数据与云端写入行为均未改变。
