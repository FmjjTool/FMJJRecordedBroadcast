# 2026-10-04 快手登录浏览器"一直登陆不了"修复

## 现象

软件内打开快手登录浏览器后，用户在手机号验证码登录流程中点击「验证/获取验证码」
按钮始终无反应（无倒计时、无报错、页面不刷新），登录流程完全卡死。

## 排查过程（全部真实浏览器实测）

### 1. 页面功能层（排除）
- account/login 直达页：扫码/密码/验证码三 Tab、手机号输入、协议勾选全部正常
- 独立窗口下点「获取验证码」：`id.kuaishou.com/pass/kuaishou/sms/requestMobileCode`
  正常发出（HTTP 200），倒计时出现
- 带存档 Cookie vs 不带：A/B 对比均正常 → Cookie 无影响

### 2. 首页入口遮挡（发现附带 bug）
- 快手新版首页左下角「立即登录」按钮在 660 视口高度下被侧栏底部「京ICP备…-136」
  备案号盒子叠住（elementFromPoint 实测命中备案按钮）——真实点击永远无效

### 3. 贴合层点击失效（根因，实锤）
用 cookie_manager._embed 同款 Win32 改造（去 WS_CAPTION/WS_THICKFRAME +
WS_EX_TOOLWINDOW + SWP_NOACTIVATE 贴合）后：
- **贴合未激活状态**：点「获取验证码」→ **零请求、无倒计时**（完全复现用户症状）
- **SetForegroundWindow 激活后**：同样点击 → 请求正常发出（200）

结论：NOACTIVATE 贴入的 Chromium 窗口从未被系统激活，处于非激活状态时会
丢弃按钮点击的事件派发（与此前"子窗口嵌入丢按键"是同一族问题：Chromium 对
窗口激活状态敏感）。键盘 Tab 切换/输入不 受影响，仅按钮 click 派发失效。

## 修复（4 处）

1. **cookie_manager.py `_embed`**：贴合置入后 `SetForegroundWindow(hwnd)` 激活
   一次（try 兜底，浏览器由本进程启动通常有前台权）。验证：激活后点击恢复有效。
2. **cookie_manager.py configs**：快手登录 URL 首页 → `account/login` 直达
   （自带完整登录弹窗，绕开首页「立即登录」被备案号遮挡的问题）。
3. **cookie_manager.py viewport**：660 → 760（快手新版页面更高，660 下侧栏
   元素互相重叠）。
4. **登录特征 + whoami**：
   - auth_keys 增加 `kuaishou.server.webday7_st`（7 天票；用户实测登录成功后
     存的是 7 天票而非 30 天票 web_st，只认后者会永远检测不到登录）
   - whoami._kuaishou：graphql userInfo 接口已失效（登录态也返回 null，恒
     ok:False）——改为 Cookie 票据判定 + ptnick hex 昵称提取
     （ptnick 实测是纯 hex UTF-8，如 e6ad86e68595 → bytes.fromhex 解码）

## 附带发现（未改）

- 存档 Cookie 含大量 QQ 授权中间态残留（qrsig/pt_login_sig/oauth_state 等，
  用户曾尝试 QQ 登录快手未完成）——不影响验证码流程，登录成功后自然覆盖
- 快手首页顶栏已无登录入口（新版 UI 改版），登录入口在左下角

## 教训

- **Chromium 贴合层三连坑**：①子窗口嵌入丢键盘 ②NOACTIVATE 贴入未激活丢
  按钮点击 ③viewport 过小页面元素互相遮挡。贴合方案必须：顶层独立窗口 +
  置入后激活一次 + 视口高度余量
- Playwright 坐标点击的按钮定位陷阱：inner 文本匹配「获取验证码」会同时命中
  输入框内小元素（中心点落在输入框上，点击无效），必须用 elementFromPoint
  校验命中目标确实是按钮
- 接口会悄悄死掉：graphql userInfo 返回 200 + data=null 而非报错，验证逻辑
  要有"接口失效"的降级路径

## 追加（同日晚）：假 Cookie / 登录后主页掉登录态

**用户复测反馈**：account/login 能登录成功，但跳转到主网址显示需要重新登录；
保存下来的 Cookie 是"假 Cookie"（采集报"快手主页需要登录"），whoami 却显示
"已登录 · 歆慕"（误报——ptnick 来自 QQ 残留票，票据判定"存在即登录"无法识别
过期票）。

**排查实测**：
- 存档（21:13 保存）解密后仍含旧 webday7_st + 全套 QQ 互联残留
  （qrsig/pt_login_sig/pt_oauth_token 等），用其开浏览器访问 account/login
  仍显示登录页 → 票据无效，本次登录的票从未真正落地/生效
- 收割逻辑 `jar[n] = val` 按 name 平铺，同名多域时后遍历的覆盖先遍历的：
  回种的旧票（.kuaishou.com）与新种的票同名时，新票可能被旧票覆盖

**修复（3 处）**：
1. `new_context` 后 `add_init_script` 覆写 `navigator.webdriver → undefined`：
   `--disable-blink-features=AutomationControlled` 抹不掉该标记（实测仍为
   true），快手登录接口检测自动化标记可能发无效票据（表面登录成功、跳主页
   即掉登录态）
2. 快手回种白名单 `_KS_LOGIN_KEEP`（did/didv/clientid/kpf/kpn/_bl_uid/
   __aegis_uid/kwfv1/ktrace-context）：过期的登录态票与 QQ 互联残留不再回种，
   避免同名覆盖新票 + 干扰登录流程；登录态全靠本次新种
3. 清除当前快手的失效存档 Cookie（whoami 误报"已登录"的来源）

**注意**：浏览器内主页显示"需要重新登录"≠ Cookie 无效——采集走 HTTP 直连
带 Cookie 头（不受页面域限制），以账号获取实测为准。

**待用户复测**：重启应用 → 快手重新登录 → 保存 → 账号获取实测。若仍拿到
假票，下一步加 Set-Cookie 响应头监听日志（抓登录响应的票据 domain，排查
新版是否把票据种成 host-only id.kuaishou.com）。
