# 性能诊断与 Rust 评估

在主窗口左下角点「性能」，进入「性能诊断」。检测默认关闭，不会自动开启 Python 分配追踪或写报告。

## 找到内存增长的位置

1. 点「开始检测」，切到要检查的页面，反复执行相同操作，然后返回诊断页。
2. 看工作集、私有提交和子进程趋势；「页面 / 任务耗时」区分页面切换、后台执行与主线程回调。「页面控件」显示已挂载或后台保留的页面、控件数和表格格数。
3. 需要定位 Python 分配时，停止检测，勾选「追踪 Python 分配（较慢）」后重新开始。先记一次「Python 快照」，复现操作，再记一次快照。「分配增长」列出两次快照间仍被保留的新增分配位置；「Python 分配」列出当前占用最多的位置。
4. 点「导出报告」保存 JSON，默认目录为统一导出目录下的「性能诊断」。停止后记录仍保留在主程序中，重新开始会清空上一轮记录；退出程序前需要自行导出。

每秒自动采样，保留最近 3600 次采样、2000 个事件和 20 份快照摘要。子进程每 5 秒更新，主界面用 100 毫秒心跳观察事件循环延迟。报告只记录数值、页面标识、函数名和分配位置，不记录业务行、Cookie、请求参数、异常正文或子进程命令行。

## 指标的含义和边界

| 指标 | 可以判断 | 不能据此判断 |
| --- | --- | --- |
| 工作集 | 当前驻留在内存中的进程页面，包括共享页面 | 页面独占内存或 Python 对象总量 |
| 私有提交 | Windows 为进程私有分配的提交量 | 全部都在物理内存中；不能与工作集相加 |
| Python 分配 / 快照 | 开启追踪之后的 Python 分配及相对上次快照的变化 | 追踪前已有对象、全部 Qt / 图片 / 原生库内存 |
| 子进程 | 当前后代进程（如 FFmpeg、浏览器）的独立内存 | 已退出或权限不足的子进程；与主进程工作集相加可能重复统计共享页面 |
| 控件 / 表格格数 | 哪些页面还在，以及页面结构规模 | 每页实际内存；模型视图的格数也不是已分配单元格数 |
| 页面切换内存增量 | 切换前后整个进程的变化 | 同期后台任务之外的页面独占增量 |
| CPU | 进程占用的逻辑核数量，100% 表示用满一个核 | 具体函数的 CPU 独占时间；后台耗时可能是在等网络或磁盘 |
| 界面延迟 | 心跳超过预期的等待时间 | 完整帧率，或所有短于心跳周期的卡顿 |

Python 追踪、快照、诊断表格自身都会占用 CPU 和内存。报告另列追踪器的 bookkeeping 内存，但这个值不是全部诊断成本。先做轻量检测，再单独开启追踪，两种模式下的耗时不能直接当作同一基准比较。操作后内存不下降可能是缓存、Python/Qt 分配器保留或真正的引用增长；需反复操作并观察相同位置的持续增长，不能仅凭一次增量判定泄漏。

## Rust 是否值得迁移

本项目的视频转换由 FFmpeg 子进程执行，Qt 控件、图片显示以及 SQLite、JSON 等已有大量原生实现。替换 Python 调度代码不会直接加速这些引擎或腾讯接口等待。优先检查重复加载、缓存、控件规模和生命周期；确认纯 Python 循环占据主要计算时间后，再考虑用 Rust 实现局部计算模块。

腾讯文档中间层的作品归一化、去重、分组及匹配（`src/toolbox/tcdoc/bridge.py`）可以作为候选，但要先用相同数据量和输出正确性要求做独立基准。当前诊断记录可以筛出慢任务；它不是每个函数的 CPU 分析器，迁移前仍需对候选任务做 CPU profiling。

无法在未测量时承诺整个应用提速多少。可用 Amdahl 定律做条件估算：

`整体加速倍数 = 1 / (1 - p + p / s)`

其中 `p` 是可以迁移的计算占总耗时的比例，`s` 是该部分实测加速倍数。下面只是假设局部计算加速 5 倍的数学示例，不是本项目 Rust 实测结果：

| 可迁移计算占总耗时 | 整体加速 | 总耗时减少 |
| --- | --- | --- |
| 20% | 约 1.19 倍 | 16% |
| 80% | 约 2.78 倍 | 64% |

内存也受占比限制。例如可迁移对象占进程内存 30%，并且 Rust 将这部分占用减半，则整体内存只减少约 15%。这也是条件估算；跨语言数据复制和接口开销可能抵消收益，应以同一操作、同一数据量的前后对照为准。
