# 约定skill（强制阅读）

## 定位

本项目最高优先级的强制约定。任何 Agent（含子 Agent、后台任务）在执行任何操作前，必须先阅读本文件并遵守全部约定；未阅读不得开始操作。

## 强制阅读规则

1. 任何 Agent 接到任务后，**第一步是阅读本 skill**，之后才允许执行其他任何动作（包括但不限于：搜索文件、制定计划、编辑代码、构建打包、发布版本）。
2. 本 skill 与任务相关 skill 同时适用：先读本 skill，再读任务对应的 skill。
3. 约定冲突时，以本 skill 为准；其中**约定 7 与 [cookie-data-protection](../cookie-data-protection/SKILL.md) 的真实 Cookie 绝对保护禁令优先于其他项目条款**。所有操作前完整阅读该 skill，不能以统一登录、备份、测试、迁移或核心模块授权放宽禁令。本 skill 未覆盖的内容，按任务相关 skill 执行。
4. 新增约定只能追加，不得删除或篡改已有条目；条目连续编号。用户明确要求修订已有约定时，只修订其指定内容并同步 `AGENTS.md`，其余条目保留。

## 约定清单

### 约定 1：更新前获取远端状态，遵循版本领先原则

**触发条件**：任何“更新”动作之前，包括但不限于修改代码、修改配置、修改资源、发布版本、重建产物等一切会变更仓库内容的操作。

**执行步骤**：

1. 按约定 2 执行 `git status`，先本地提交备份已有修改/未跟踪业务文件。完整阅读、状态检查、备份及同步本身属于本次编辑前的准备动作，不要求先合并才能备份。
2. 执行 `git remote -v`，`origin` 的获取与推送地址均必须为 `https://github.com/FmjjTool/FMJJRecordedBroadcast.git`；确认当前工作分支。非 `main` 分支不得直接拿 `origin/main` 的分叉计数当作同一分支的版本领先：先确认用户要求的目标分支及其远端对应关系。
3. 执行 `git fetch origin`。必须成功取得本次远端状态，不用可能直接合并分叉的普通 `git pull` 代替此步骤。
4. 对本项目 `main` 执行 `git rev-list --left-right --count HEAD...origin/main`，结果左数为本地独有提交、右数为云端独有提交。结合 `git merge-base HEAD origin/main` 判断提交祖先关系；没有共同祖先、目标引用缺失或比较失败时停止并向用户说明。
5. 按下表决定本次编辑基础。领先以 Git 历史为依据，不能用文件修改时间、提交日期、应用版本号或提交总数猜测；本地未提交改动须先备份再参与比较。

| 本地独有 | 云端独有 | 状态 | 必须执行 |
| --- | --- | --- | --- |
| 0 | 0 | 两端一致 | 继续本次本地编辑 |
| 大于 0 | 0 | 本地领先 | 保留当前本地提交，优先更新本地较新代码；无需把云端旧代码重新写入本地 |
| 0 | 大于 0 | 云端领先 | `git merge --ff-only origin/main` 快进本地；成功且工作区正常后再编辑 |
| 大于 0 | 大于 0 | 双方分叉 | 列出差异并向用户提问；等待明确选择前不开始本次编辑、不合并、不覆盖、不推送 |

本地领先仅决定开发基础，不自动授权推送、发布或更新其他云端部署。双方修改不同文件、表面可自动合并，也仍按分叉处理。再次准备推送时重新 fetch 和比较，防止工作期间云端新增提交；仅为检查不会触发发布流程。

**双方分叉时列出差值/差异（含新增、删除行）**：

1. 记录本地 `HEAD`、云端 `origin/main`、共同基线的提交哈希及双方独有提交摘要：`git log --left-right --oneline HEAD...origin/main`。
2. 分别读取共同基线到本地、共同基线到云端的 `git diff --name-status`、`git diff --numstat` 和相关文本差异；不能只列提交数或只看两端最终内容。对于删除/改名、二进制或无法合并的内容，明确说明。
3. 逐文件列出下表，并对同一文件的重叠修改展示具体片段、冲突点和功能影响；只在内存/只读差异中分析，不为探测冲突先执行会改变当前工作区的合并。

| 文件/模块 | 本地新增/删除行与功能变化 | 云端新增/删除行与功能变化 | 重叠或冲突 | 建议保留与舍弃、理由 |
| --- | --- | --- | --- | --- |
| 按实际差异填写 | 基线 → 本地 | 基线 → 云端 | 无重叠/具体冲突内容 | 逐项提出合并方案 |

4. 附上可审阅的方案后向用户提问：「本地与云端都有独立改动。请选择覆盖云端、覆盖本地，或合并两者最优；建议合并的逐项取舍见上表。」推荐有理由的方案，不能以“最优”为由自动合并；用户答复前保持等待，仅可继续只读分析。

**确认后的处理**：

- 覆盖云端：以用户确认范围内的本地内容为准，先保存双方提交引用，再形成保留双方历史的协调提交；该选择授权范围内的云端同步，但不附带版本递增、打包或 Release。推送前重新核对远端，出现新的分叉或未列出的改动时再次列出差异并询问。
- 覆盖本地：保存可恢复的本地备份引用，以用户确认范围内的云端内容替换本地，保留本地历史，不自动把结果推回云端。
- 合并两者最优：按已列出的取舍保留双方有效修改，解决重叠后运行适用验证、更新当日报告并本地提交；是否推送以用户指示为准。
- “覆盖”表示选择最终内容，不等于删除提交历史。不得使用强制推送；不得未经确认扩大为整库覆盖。任何新冲突或偏离已确认方案的取舍，重新展示差异并询问。

**获取、比较或同步失败处理**（网络不可达、认证失败、合并冲突、备份失败、非 git 仓库、远端不匹配等）：

1. **立即停止本次编辑及同步变更**，禁止在未核对远端的旧状态上继续修改。
2. 向用户说明实际失败原因并给出适用选项（重试 / 处理本地改动 / 确认分支或仓库 / 取消更新），或按适用 skill 处理；不能跳过成功 fetch 和版本比较。
3. 禁止把失败当作“已是最新”、绕过备份/同步，或使用 `git push --force`、强制推送的其他形式等破坏远端历史的操作。

### 约定 2：改动前先备份，完成后必须本地提交

**执行前检查（任何更改操作之前）**：

1. 执行 `git status`，检查当前代码是否已有备份（即已保存为本地 `commit`）。
2. 若存在已修改或未跟踪文件（未备份），先本地 `git commit` 完成备份，再开始更改；提交前清理临时文件与测试产物。
3. 若无法提交（非 git 仓库、合并冲突、钩子失败等），**立即停止**并向用户提问，禁止直接改动。

**完成后提交**：

1. 每次任务或编辑部分完成后，必须本地 `git commit` 一次，不遗漏。
2. 提交信息需说明本次改动内容；提交后 `git status` 应无未备份的业务改动。
3. 向用户汇报本部分改动摘要与提交哈希。
4. 本地提交不等于推送；推送需用户明确指示或按相关 skill（如 `summarize-update`）执行。

### 约定 3：技能只写 Markdown 文档

**适用范围**：新增 skill、修改 skill、把流程/约定沉淀为 skill 的一切场景。

**执行要求**：

1. skill 只用 Markdown 表达：`src/skills/<skill-name>/SKILL.md`，需要拆分时只用 `.md` 子文档（references、附录等也用 `.md`）。
2. 禁止附带可执行脚本（`.py`、`.js`、`.ps1`、`.sh`、`.bat` 等）、机器可读配置（`.json`、`.yaml`、`.toml`、`.ini` 等）、二进制或任何需要运行才能生效的校验程序。
3. 约束、白名单、校验规则全部写在正文里，由 Agent 阅读后逐项人工核对；不得把判断逻辑外包给脚本。
4. 例外：用户明确告知需要脚本或结构化配置时才可添加，且只对当次需求生效；下一次改动该 skill 时按下述第 5 条清理。
5. 已存在的非 md 附属文件（历史遗留），在下次改动该 skill 时一并移除。

**禁止事项**：

- 禁止以"提高准确性""方便自动化校验"为由给 skill 加脚本或 JSON。
- 禁止新增 skill 时携带非 md 文件。
- 禁止把 md 里的关键规则只写在脚本里、正文不留。

### 约定 4：完成后必须写当日报告，同一天只保留一份

**触发条件**：本项目每次任务或编辑部分完成后，包括只读检查、文档编辑、代码修改和后续验证。

**执行要求**：

1. 按北京时间（`Asia/Shanghai`）的完成日期确定报告日期，统一使用项目根目录 `Progress/YYYY-MM-DD_当日总结.md`。跨日完成的事项写入实际完成当天的总结。
2. 同一天只保留一份当日总结；多个任务、多次编辑、分部分完成和后续验证都追加或更新到同一文件，不按任务主题、Agent 或编辑次数拆成多份。
3. 更新前重新读取已有当日总结，保留其他任务的记录，只追加本次内容或更新本次条目。当天已有其他主题报告时，先完整合并原文并核对无遗漏，再移除当天重复的报告文件。
4. 报告包含需求、处理方案、改动文件、验证结果、待处理问题及 Git 提交信息。未完成的事项、未执行的验证如实标注，不写成已完成或已通过。
5. 收尾顺序为：完成本次适用的检查 → 更新当日报告 → 连同本次改动一起本地 `git commit` → 向用户汇报结果及实际提交哈希。只读任务也需将报告本地提交。
6. 已有提交可以记录实际哈希；报告自身的提交记录提交说明，提交后的实际哈希在回复中汇报，不为补写自身哈希反复提交。任务要求的专用输出格式用于任务产物，项目执行报告单独保存在当日总结中。

**与其他 skill 的衔接**：其他 skill 的进度记录、执行汇报和收尾记录应汇入同一当日总结；原有按任务主题命名 `YYYY-MM-DD_主题.md` 或同日另建报告的要求，由本条统一为一天一份。

### 约定 5：账户登录统一由 Cookie 管理提供接口

**触发条件**：新增/修改任何账户登录、Cookie/Token 保存与获取、登录验证、需要认证的业务请求，以及登录快照或旧登录文件迁移。

**约定 7 优先**：下述登录管理、清除与迁移属于能力设计，不能作为操作真实已存 Cookie 的授权。Agent 只能只读使用已确认无写入副作用的有效凭据接口；所有保存、清除、换号、刷新、迁移的验证必须在独立临时目录使用虚构数据，不能对真实存储执行。

1. 先完整阅读 [cookie-manager](../cookie-manager/SKILL.md)，所有需要登录的账户统一纳入「Cookie 管理」；包括现有平台、新平台及 GitHub 等使用 Token 的账户，按原生认证方式接入。
2. 登录、重新登录、账号选择/切换、状态验证与清除统一由管理入口和认证管理层负责；业务页面需要登录时打开/跳转到该入口。
3. 业务只调用管理层接口获取当前有效凭据；已有 Cookie 走 `src/auth.py` 的 `get_cookie(platform)` 等适用入口。禁止业务直接读取登录文件、另设凭据存储或硬编码凭据。
4. 非 Cookie 登录所需的 Token、会话及 localStorage 由管理层平台适配提供；接口缺失时先扩展统一管理能力再接业务，不把 Token 冒充 Cookie，也不虚构已存在的接口。
5. 关闭、过期、清除与账号切换对所有调用方一致生效；缓存不得绕过管理层恢复旧登录。用户凭据不得写入源码、skill、报告、日志、提交或发行包。
6. 既有独立登录逻辑在涉及该链路的任务中按 skill 迁移、核对并验证；未迁移项如实登记，新增文档不能宣称实际代码已经全部统一。

### 约定 6：录播工具箱八个核心模块默认禁止改动

1. 任何更新前，完整阅读 [recording-toolbox-core](../recording-toolbox-core/SKILL.md)，按其模块、路由及代码映射核对影响。用户指定的八个模块为核心逻辑处理中心：**自动整理、交互重命名 / 投稿、视频操作、音频提取、字幕转换、继续操作、日历浏览、文件迁移**。
2. 未经用户针对本次具体模块及改动范围明确授权，禁止修改这些模块的菜单入口、顺序、路由、页面/交互、底层处理逻辑、参数、文件读写及关联处理引擎；旧别名、嵌入页签和子窗口同样受限。
3. 通过共享配置、工具函数、主题、生命周期或其他模块间接改变上述核心，也属于核心改动。全局美化、优化、重构、清理、修复或约定 5 的登录统一，不自动授权更改核心；在保护区外继续可独立完成的工作。
4. 允许只读检查、分析差异、编写规则文档与按约定 2 保存既有改动的备份，不自动撤销已有代码。发现核心缺陷时先记录、分析并给出具体改动方案；用户尚未授权该具体范围则询问，明确授权已覆盖时无需重复确认。
5. 获准后仅处理指定模块、文件与功能范围，保留其余核心功能；按本 skill 完成验证、当日报告与本地提交。新增文档不等于运行时已经锁定代码，必须由每个 Agent 阅读并人工核对执行。

### 约定 7：已保存的真实 Cookie 绝对禁止改动（强制中的强制）

1. 所有操作前完整阅读 [cookie-data-protection](../cookie-data-protection/SKILL.md)。这是项目内最高级别的数据保护禁令：**所有 Agent、子 Agent、自动任务都绝对不能改动 Cookie 管理器已经保存的真实 Cookie**。
2. 禁止写入、覆盖、删除、清空、刷新、迁移、重排或重新加密真实 Cookie，禁止改变平台/账号绑定、保存时间、加密表示、密钥或使旧数据失效的加密规则；真实存储文件整体受保护，不能因只改开关、增加平台或规范格式而重新写回。
3. 禁止经登录窗口、扫码、浏览器回种、接口 `Set-Cookie`、登录快照、旧文件迁移、配置导入、备份恢复、清理、卸载重装或打包间接修改。名称像“读取/验证”的函数若可能迁移、回写或清除，也不能对真实环境调用。
4. 不设置临时授权、确认后覆盖、测试、修复、迁移等例外；约定 5 的登录统一与约定 6 的具体模块授权不解除此数据禁令。需要修改真实 Cookie 的事项停止并说明规则，不将覆盖真实凭据作为默认询问选项。
5. 只允许通过无写入副作用的接口在内存中使用已有有效凭据，不输出内容；验证写入/清除/切换等流程仅用独立临时目录及虚构凭据，禁止从真实环境复制 Cookie。无法确认副作用或隔离范围时停止相关执行，继续静态分析和独立工作。
6. 真实凭据不得进入 Git、日志、报告、导出或发行包；约定 2 的源码备份不包含凭据文件。不得为新增禁令而自动改真实凭据文件、加密格式或权限。发现意外变化时停止并记录不含凭据内容的证据，不自行回写或回滚。
7. 按约定 4 报告实际执行边界；没有运行时拦截器时如实说明，不能把 skill 目录发现写成应用已锁定 Cookie 数据。

### 约定 8：总结文章必须携带文件，总结工作排除自动推送

1. 用户实际请求以「总结文章」为关键词总结文件时，先完整阅读 [summarize-article](../summarize-article/SKILL.md)。请求必须携带待总结文件（附件或明确可访问的文件路径）；没有文件、无法读取或多个文件目标不明确时提示补充/明确，不能凭空生成。
2. 总结前完整阅读 [fengming-livestream-summary](../fengming-livestream-summary/SKILL.md)，以及其中的纠错表、分类库、输出模板和数据库索引，按需读取相关快照；依指定规则处理完整文件内容，不仅凭记忆、文件名、预览或部分片段总结。
3. 创建/修改/解释关键词或 skill 的任务不触发实际文件总结，不要求文章附件。工作总结与文件总结区分：普通工作总结无需因本条额外提供文章文件，也不自动套用直播维度。
4. **总结类工作排除自动推送**：总结文章、直播总结、工作总结及更新内容汇总（含仅要求「总结此次更新」），默认不执行 `git push`、打包、递增版本或创建 tag/Release；引用、解释或否定推送词汇不构成推送授权。只有用户另外明确要求推送/发布时才按其具体范围处理。
5. 约定 2、4 的必要本地提交与当日报告继续适用，本地提交不等于推送。总结正文遵守指定输出格式，执行记录汇入唯一当日报告，不把 Git/发布说明混入正文。

### 约定 9：页面不得自建 Cookie 管理器，也不得出现 Cookie 字样

**触发条件**：新增或修改任何页面、对话框、浮层、子窗口、嵌入式页签，以及其中的文案、按钮、链接、提示、状态与报错。

1. 全项目只保留一个 Cookie 管理入口，即统一「Cookie 管理」总管理器（`src/gui_qt/cookie_manager.py` 的 `CookieManagerDialog` 与 `COOKIE_PLATFORMS`）。任何页面都不得另行创建 Cookie 管理器、登录窗口、凭据输入/保存控件，也不得维护第二套凭据列表。
2. 页面不得放置「打开 Cookie 管理」「去登录」「Cookie 管理」等入口按钮、链接、提示或引导文案；页面也不得自行弹出或嵌入登录界面。需要登录的用户自行前往总管理器，页面不承担引导职责。
3. 页面展示给用户的文案（标题、说明、提示、tooltip、状态栏、报错、可见日志）不得出现「Cookie」「cookie」及同类凭据字样，不得展示凭据文件名或存储路径。未登录时只按功能需要走公开/游客流程，或给出不含凭据名词的「需要登录」类提示。
4. 业务页面只通过管理层接口（如 `src/auth.py` 的 `get_cookie(platform)` 等）只读获取当前登录态；不代用户登录，不保存、刷新、迁移或清除凭据，不直接读取凭据文件。新增平台或凭据类型只扩展总管理器与平台适配，不在业务页面加入口。
5. 本条不解除约定 7，也不自动回滚既有页面。既有页面中已经存在的 Cookie 字样、登录引导或自建管理入口，在涉及该页面改动时按本条清理；未获得针对该页面的具体授权时不批量修改。

### 约定 10：定时任务统一由「任务」页管理，功能页不得内嵌定时设置

**触发条件**：新增/修改任何需要定时执行的采集、备份、统计等功能，或调整计划模式、时间、间隔。

1. 全项目只保留一个定时任务设置入口：`src/gui_qt/pages/tasks.py` 的「⏰ 定时任务」页。计划模式（每天 / 按间隔）、时间、间隔的修改与安装 / 删除都在该页完成。
2. 功能页（腾讯文档监控、账号追踪、网盘备份、本地资料站等）不得再放置「安装/更新定时」「删除定时」「定时采集时间 / 间隔」等控件或弹窗；只允许保留一句不含设置控件的说明文案（如「定时设置已统一到任务页」）。
3. 新增定时任务必须先注册到 `src/toolbox/task_center.py`：补配置键映射、`list_tasks()` 行、`get_schedule()` / `save_schedule()` / `install()` / `uninstall()` 分发以及安装模块；任务页通过该中心读写，不直接调用各任务模块。
4. 任务页「设置」对话框保存后必须调用 `task_center.install()` 立即注册 / 更新 Windows 计划任务，并刷新安装状态与下次运行时间。
5. 软件内会话计时器（如「信息获取」页运行期间的定时获取）不属于 Windows 计划任务，不强行迁移；但不得伪装成计划任务入口，文案需说明仅在软件打开期间生效。
6. 本条只改设置入口，不改变既有任务名与配置键，避免已安装任务失效。
