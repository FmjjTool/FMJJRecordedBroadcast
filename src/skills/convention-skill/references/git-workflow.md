# Git、Markdown 与报告执行细则

入口与触发见 [总约定](../SKILL.md)，只加载当前任务涉及的章节；不得据细则扩大任务授权。

### 约定 1：更新前获取远端状态，遵循版本领先原则

**触发条件**：任何“更新”动作之前，包括但不限于修改代码、修改配置、修改资源、发布版本、重建产物等一切会变更仓库内容的操作。

**执行步骤**：

1. 按约定 2 执行 `git status`，先本地提交备份本任务拥有且已稳定的修改 / 未跟踪业务文件；他人在途 WIP 按协作规则隔离，不擅自暂存或提交。完整阅读、状态检查、备份及同步本身属于本次编辑前的准备动作，不要求先合并才能备份。
2. 执行 `git remote -v`，`origin` 的获取与推送地址均必须为 `https://github.com/FmjjTool/FMJJRecordedBroadcast.git`；确认当前工作分支。非 `main` 分支不得直接拿 `origin/main` 的分叉计数当作同一分支的版本领先：先确认用户要求的目标分支及其远端对应关系。
3. 执行 `git fetch origin`。必须成功取得本次远端状态，不用可能直接合并分叉的普通 `git pull` 代替此步骤。
4. 对本项目 `main` 执行 `git rev-list --left-right --count HEAD...origin/main`，结果左数为本地独有提交、右数为云端独有提交。结合 `git merge-base HEAD origin/main` 判断提交祖先关系；没有共同祖先、目标引用缺失或比较失败时停止并向用户说明。
5. 按下表决定本次编辑基础。领先以 Git 历史为依据，不能用文件修改时间、提交日期、应用版本号或提交总数猜测；本地未提交改动须先备份再参与比较。

| 本地独有 | 云端独有 | 状态 | 必须执行 |
| --- | --- | --- | --- |
| 0 | 0 | 两端一致 | 继续本次本地编辑 |
| 大于 0 | 0 | 本地领先 | 保留当前本地提交，优先更新本地较新代码；无需把云端旧代码重新写入本地 |
| 0 | 大于 0 | 云端领先 | `git merge --ff-only origin/main` 快进本地；成功且工作区正常后再编辑 |
| 大于 0 | 大于 0 | 双方分叉 | 列出差异并向用户提问；等待明确选择前不开始本次编辑、不合并、不覆盖、不推送 |

本地领先仅决定开发基础，不自动授权推送、发布或更新其他云端部署。双方修改不同文件、表面可自动合并，也仍按分叉处理。再次准备推送时重新 fetch 和比较，防止工作期间云端新增提交；仅为检查不会触发发布流程。

**双方分叉时列出差值/差异（含新增、删除行）**：

1. 记录本地 `HEAD`、云端 `origin/main`、共同基线的提交哈希及双方独有提交摘要：`git log --left-right --oneline HEAD...origin/main`。
2. 分别读取共同基线到本地、共同基线到云端的 `git diff --name-status`、`git diff --numstat` 和相关文本差异；不能只列提交数或只看两端最终内容。对于删除/改名、二进制或无法合并的内容，明确说明。
3. 逐文件列出下表，并对同一文件的重叠修改展示具体片段、冲突点和功能影响；只在内存/只读差异中分析，不为探测冲突先执行会改变当前工作区的合并。

| 文件/模块 | 本地新增/删除行与功能变化 | 云端新增/删除行与功能变化 | 重叠或冲突 | 建议保留与舍弃、理由 |
| --- | --- | --- | --- | --- |
| 按实际差异填写 | 基线 → 本地 | 基线 → 云端 | 无重叠/具体冲突内容 | 逐项提出合并方案 |

4. 附上可审阅的方案后向用户提问：「本地与云端都有独立改动。请选择覆盖云端、覆盖本地，或合并两者最优；建议合并的逐项取舍见上表。」推荐有理由的方案，不能以“最优”为由自动合并；用户答复前保持等待，仅可继续只读分析。

**确认后的处理**：

- 覆盖云端：以用户确认范围内的本地内容为准，先保存双方提交引用，再形成保留双方历史的协调提交；该选择授权范围内的云端同步，但不附带版本递增、打包或 Release。推送前重新核对远端，出现新的分叉或未列出的改动时再次列出差异并询问。
- 覆盖本地：保存可恢复的本地备份引用，以用户确认范围内的云端内容替换本地，保留本地历史，不自动把结果推回云端。
- 合并两者最优：按已列出的取舍保留双方有效修改，解决重叠后运行适用验证、更新当日报告并本地提交；是否推送以用户指示为准。
- “覆盖”表示选择最终内容，不等于删除提交历史。不得使用强制推送；不得未经确认扩大为整库覆盖。任何新冲突或偏离已确认方案的取舍，重新展示差异并询问。

**获取、比较或同步失败处理**（网络不可达、认证失败、合并冲突、备份失败、非 git 仓库、远端不匹配等）：

1. **立即停止本次编辑及同步变更**，禁止在未核对远端的旧状态上继续修改。
2. 向用户说明实际失败原因并给出适用选项（重试 / 处理本地改动 / 确认分支或仓库 / 取消更新），或按适用 skill 处理；不能跳过成功 fetch 和版本比较。
3. 禁止把失败当作“已是最新”、绕过备份/同步，或使用 `git push --force`、强制推送的其他形式等破坏远端历史的操作。

### 约定 2：改动前先备份，完成后必须本地提交

**执行前检查（任何更改操作之前）**：

1. 执行 `git status`，检查当前代码是否已有备份（即已保存为本地 `commit`）。
2. 若存在本任务拥有且已稳定的已修改或未跟踪文件（未备份），先本地 `git commit` 完成备份，再开始更改；提交前清理临时文件与测试产物。
3. 并行任务的在途 WIP 不擅自暂存或提交；先协调文件所有权，或以已核对历史的 HEAD 创建独立干净 worktree，只编辑本任务文件。独立树完成后按明确路径合回，保留原树 WIP 与暂存状态。不能安全隔离时停止冲突部分。
4. 若无法提交（非 git 仓库、合并冲突、钩子失败等），**立即停止**并向用户提问，禁止直接改动。

**完成后提交**：

1. 每次任务或编辑部分完成后，必须本地 `git commit` 一次，不遗漏。
2. 提交信息需说明本次改动内容；提交后按本次文件范围检查 git status；共享树的他人 WIP 保留并报告，不要求为清空状态而提交或删除它们。
3. 向用户汇报本部分改动摘要与提交哈希。
4. 本地提交不等于推送；推送需用户明确指示或按相关 skill（如 `summarize-update`）执行。

### 约定 3：技能只写 Markdown 文档

**适用范围**：新增 skill、修改 skill、把流程/约定沉淀为 skill 的一切场景。

**执行要求**：

1. skill 只用 Markdown 表达：`src/skills/<skill-name>/SKILL.md`，需要拆分时只用 `.md` 子文档（references、附录等也用 `.md`）。
2. 禁止附带可执行脚本（`.py`、`.js`、`.ps1`、`.sh`、`.bat` 等）、机器可读配置（`.json`、`.yaml`、`.toml`、`.ini` 等）、二进制或任何需要运行才能生效的校验程序。
3. 约束、白名单、校验规则全部写在正文里，由 Agent 阅读后逐项人工核对；不得把判断逻辑外包给脚本。
4. 例外：用户明确告知需要脚本或结构化配置时才可添加，且只对当次需求生效；下一次改动该 skill 时按下述第 5 条清理。
5. 已存在的非 md 附属文件（历史遗留），在下次改动该 skill 时一并移除。

**禁止事项**：

- 禁止以"提高准确性""方便自动化校验"为由给 skill 加脚本或 JSON。
- 禁止新增 skill 时携带非 md 文件。
- 禁止把 md 里的关键规则只写在脚本里、正文不留。

### 约定 4：完成后必须写当日报告，同一天只保留一份

**触发条件**：本项目每次任务或编辑部分完成后，包括只读检查、文档编辑、代码修改和后续验证。

**执行要求**：

1. 按北京时间（`Asia/Shanghai`）的完成日期确定报告日期，统一使用项目根目录 `Progress/YYYY-MM-DD_当日总结.md`。跨日完成的事项写入实际完成当天的总结。
2. 同一天只保留一份当日总结；多个任务、多次编辑、分部分完成和后续验证都追加或更新到同一文件，不按任务主题、Agent 或编辑次数拆成多份。
3. 更新前重新读取已有当日总结，保留其他任务的记录，只追加本次内容或更新本次条目。当天已有其他主题报告时，先完整合并原文并核对无遗漏，再移除当天重复的报告文件。
4. 报告包含需求、处理方案、改动文件、验证结果、待处理问题及 Git 提交信息。未完成的事项、未执行的验证如实标注，不写成已完成或已通过。
5. 收尾顺序为：完成本次适用的检查 → 更新当日报告 → 连同本次改动一起本地 `git commit` → 向用户汇报结果及实际提交哈希。只读任务也需将报告本地提交。
6. 已有提交可以记录实际哈希；报告自身的提交记录提交说明，提交后的实际哈希在回复中汇报，不为补写自身哈希反复提交。任务要求的专用输出格式用于任务产物，项目执行报告单独保存在当日总结中。

**与其他 skill 的衔接**：其他 skill 的进度记录、执行汇报和收尾记录应汇入同一当日总结；原有按任务主题命名 `YYYY-MM-DD_主题.md` 或同日另建报告的要求，由本条统一为一天一份。

### 约定 15：GitHub 访问网络顺序（直连 → 代理 → 其他）

**触发条件**：任何访问 GitHub 的动作，包括 `git fetch` / `pull` / `push` / `clone`、`api.github.com`、`uploads.github.com`、Release 资产上传与下载、版本检查。

1. **第一档：直连**。默认先直连，并显式清空代理，不让仓库或环境里残留的 `http.proxy` / `https.proxy` 参与：

   ```bash
   git -c http.proxy= -c https.proxy= fetch origin
   git -c http.proxy= -c https.proxy= push origin main
   ```

   PowerShell 里先保存环境代理候选，再为本次请求临时清空（PS 5.1 无 -NoProxy）；使用后恢复宿主原值，不长期改变会话设置：
   `$env:HTTP_PROXY = $null; $env:HTTPS_PROXY = $null; $env:ALL_PROXY = $null`
   并在调用前 `[System.Net.WebRequest]::DefaultWebProxy = $null`。

2. **第二档：代理回退**。只在直连失败（DNS 解析失败、连接超时、连接被重置、TLS 握手失败、443 不通）后才切代理，按下列顺序取第一个可用项：
   1. 用户当次明确给出的代理，或环境变量 `HTTPS_PROXY` / `ALL_PROXY`；
   2. 本机常见端口：`7890`（Clash）、`10809`（v2rayN）、`12450`（旧配置，常已失效）；
   3. `git config --get http.proxy` 里的值（只当候选，不直接信任）。

   ```bash
   git -c http.proxy=http://127.0.0.1:7890 -c https.proxy=http://127.0.0.1:7890 push origin main
   ```

   切档前先探测端口：`curl -x http://127.0.0.1:7890 -sSI -m 10 https://github.com`（或 PowerShell `Test-NetConnection 127.0.0.1 -Port 7890`），端口不通的候选直接跳过，不算「代理失败」。

3. **第三档：其他方式**。前两档都失败后才用，且必须先向用户说明再执行：
   - 交回宿主/桌面环境执行同一条命令（沙箱报 DNS、`Schannel`、`SEC_E_NO_CREDENTIALS` 等网络或系统错误时，优先按此重试一次）；
   - SSH over 443：`ssh -T -p 443 git@ssh.github.com`，不持久修改 remote；对已确认目标的单次命令使用临时 URL `ssh://git@ssh.github.com:443/FmjjTool/FMJJRecordedBroadcast.git`；
   - GitHub 加速/镜像域名只允许用于只读 GET，不用于 push，也不写进 `.git/config` 长期配置。

4. **逐档推进、留下证据**：一次只升一档，记录每档真实错误（DNS / 超时 / 连接重置 / TLS / HTTP 状态码）。禁止多档并发混用，禁止静默换档不说，禁止把代理地址长期写进 `.git/config`（本机历史配置 `socks5h://127.0.0.1:12450` 指向不存在的代理，已多次导致推送失败）。

5. **三档都失败**：按约定 1 的失败处理，停止本次操作，向用户报告错误原文与已尝试的档位；不得略过 fetch/比较直接发布，也不得使用 `git push --force` 等破坏远端历史的操作。
