# 隔离测试与真实数据还原（Isolated Testing & Data Restore）

先阅读 [convention-skill](../convention-skill/SKILL.md)、[running-instance-guard](../running-instance-guard/SKILL.md)、[testing-quality-gates](../testing-quality-gates/SKILL.md)。涉及凭据时按 [cookie-data-protection](../cookie-data-protection/SKILL.md) 与 [cookie-manager](../cookie-manager/SKILL.md) 执行；涉及清理时按 [test-cleanup](../test-cleanup/SKILL.md)。

本 skill 规定「测试跑在哪里、能不能碰用户的数据、碰完怎么还回去」。它是强制规则，不是建议。

## 一、四条铁律

1. **默认隔离**：任何人工测试、UI 冒烟、截图、演示、联调，默认在隔离版本的程序里执行——独立程序副本、独立 `config/`、`download/`、`logs/`、独立端口。不得默认在项目真实目录启动，也不得连接用户正在使用的实例。
   - 真实 `config/` 与 `download/` **一律只读**：禁止在主工作区运行会创建、初始化或改写配置的命令/脚本（包括「只看一眼配置」的读取，优先在副本进行）；脚本夹具、测试数据、截图、导出只能写副本或 `_smoking/`。
   - 任何清理只删副本；真实目录出现非预期变化时立即停止并如实报告。
2. **接入需申请**：确需接入用户当前运行的实例、读取/写入真实配置与数据库、驱动真实界面或触发真实平台写入时，必须先向用户提出申请并说明范围；未得到当次明确同意前不得操作。只读查看进程、端口、窗口是否存在与日志尾部，不算接入。
3. **测试前必须快照**：任何被批准的真实环境操作，开始前必须对受影响的数据做文件级快照（数据库用一致性备份）与哈希清单；没有快照不得开始写入。
4. **测试后必须还原**：测试结束（无论成功、失败、中断、Agent 退出）都必须按快照完整还原并校验一致。**禁止用「把测试主播删掉」「把测试项清理掉」代替还原**——这正是用户反复需要重新删除、重新添加直播录制主播的原因。还原不了就停下来如实报告，不得隐瞒。

真实 Cookie 永远不在此列：即使获得接入授权，也不得改动、复制、导出已保存的真实 Cookie（约定 7）。

## 二、什么算「隔离版本」

同时满足以下全部条件才算隔离，缺一项都可能污染用户环境：

| 维度 | 要求 |
| --- | --- |
| 程序根 | 独立目录（`_smoking/isolated/<任务名>/`），不是项目真实根目录 |
| 数据根 | 副本自己的 `config/`、`download/`、`logs/`，启动后自动创建；不得指向真实目录 |
| 凭据 | 不复制真实 `config/cookies.json` 或任何登录快照；需要登录态时只读调用管理层接口，或使用虚构凭据 |
| 端口 | 需要 WebUI 时用独立端口（如 `--webui-port 18765`），先确认端口未被用户实例占用 |
| 进程 | 新进程、独立生命周期；关闭它不影响用户正在使用的实例 |
| 输出 | 截图、导出、测试数据都落在副本或 `_smoking/`，不写真实 `download/` |

本项目**没有 `--work-dir` 之类的数据目录参数**：`get_app_root()` 决定 `config/`、`download/`、`logs/`，开发模式跟随程序文件所在根，打包态跟随 exe 所在目录。因此隔离的可行方式是**运行程序副本**，而不是给原程序换工作目录。

## 三、隔离实例的标准做法

### 1. 复制当前工作树（可测试未提交改动）

```bash
mkdir -p _smoking/isolated/<任务名>
cp -a main.py src _smoking/isolated/<任务名>/
```

或整树复制并排除运行数据与版本库（单行命令，Git Bash 中直接执行）：

```bash
robocopy . "_smoking/isolated/<任务名>" /E /XD .git config download logs models _smoking build build_full_vendor dist __pycache__ .pytest_cache /XF *.pyc
```

（robocopy 返回 1–7 都表示复制成功，不要当成失败。）

若只验证已提交代码，也可用 `git worktree add --detach _smoking/iso-wt HEAD` 得到干净副本；验证结束按 `test-cleanup` 移除，不删除用户数据。

### 2. 启动前确认数据根

```bash
cd _smoking/isolated/<任务名>
python -c "import sys; sys.path.insert(0,'src'); from toolbox.config_manager import get_app_root, get_config_dir; print(get_app_root()); print(get_config_dir())"
```

输出必须位于副本目录内。若指向项目真实 `config/`，立即停止，说明复制或启动方式有误，修复后再测试。

### 3. 在副本里伪造测试数据

- 直播录制：在副本 `config/live_record.json` 里手工写假主播（虚构房间号、假备注），不要复制真实主播列表。
- 数据库：使用副本内新建的空库；需要样本时构造最小 fixture，不复制真实 `collected.db`、`increment.db` 等。
- 媒体文件：生成几秒的测试视频 / 音频放进副本 `download/`，不要指向真实下载目录。
- 大模型只读共享（可选）：必要时用 junction / 符号链接指回真实 `models/`，仅限只读；不得在副本里触发模型下载或写入真实目录。

### 4. 运行与迭代

- 桌面端：在副本目录执行 `python main.py`，启动的是新进程，不影响用户实例。
- WebUI：`python main.py --webui --webui-port 18765`，先用 `netstat -ano | grep 18765` 确认端口空闲。
- 修改源码后把改动同步进副本再重启副本；不要只在副本里改代码而忘记回写主工作区，也不要把主工作区改到一半就复制。
- Agent 自己创建的隔离实例可以自行关闭；用户正在使用的实例一律不得关闭、重启或结束进程（running-instance-guard）。
- 截图与过程产物放 `_smoking/`；只有最终报告证据截图才放 `Progress/ui/<日期>/`。

### 5. 收尾

- 按 `test-cleanup` 清理由本次测试生成的缓存与临时产物；`_smoking/` 已忽略、不提交、不推送。
- 隔离副本中的 `config/` 属于测试数据，可随副本清理；不得把副本内容复制回真实 `config/`。

## 四、接入用户当前实例 / 真实数据的申请

### 1. 先判断是否真的必要

能通过隔离副本复现、能只读分析、能写单测证明的，一律走隔离路径，不申请接入。只有以下情形才考虑申请：

- 必须在用户已经打开的真实窗口里操作，隔离实例无法体现（如真实运行中的托盘、录制状态、已加载的缓存）。
- 真实数据的规模 / 结构无法用 fixture 构造，且只读验证会直接影响结论。
- 用户明确要求在该实例上演示或验证。

### 2. 申请必须写清六项

1. **目的与必要性**：为什么隔离实例做不到。
2. **目标与范围**：哪个实例 / 窗口 / 进程；只读还是写入；具体页面与操作。
3. **数据清单**：会读取或改动的文件、数据库、计划任务。直播录制相关必须点名 `config/live_record.json`、`config/live_rooms.json`、`config/bili_live.json`、`config/douyin_live.json`、`config/douyin_live_rooms.json` 中实际涉及者。
4. **快照方案**：快照位置、覆盖文件、哈希记录方式。
5. **还原方案**：怎么还、何时还（是否需要用户先关闭软件）、怎么校验。
6. **风险与时长**：录制 / 采集中断风险、预计持续时间；说明不会关闭或重启实例（除非用户另行授权关闭）。

用户当次明确同意后才可执行；未回复、只回复「看一下」「试试」都不构成写入授权。用户同意只覆盖本次列出的范围，不自动扩大到其他页面、账号或表格。

申请可直接套用：

```text
申请接入真实实例测试：
- 目的与必要性：……
- 目标与范围：……（窗口 / 页面 / 只读或写入）
- 数据清单：……（含 config/live_record.json 等具体文件）
- 快照方案：……（_smoking/real-snapshots/<目录>，SHA-256 清单）
- 还原方案与校验：……（何时还、是否需要你先关闭软件）
- 风险与时长：……（录制 / 采集中断风险，预计 X 分钟）
请确认是否允许本次操作。
```

### 3. 接入期间仍然禁止

- 不得改动、复制、导出真实 Cookie 或登录快照（约定 7，无例外）。
- 不得关闭、重启、结束用户实例；需要重启才能还原时，由用户自己操作（running-instance-guard）。
- 不得写入腾讯文档白名单之外的表格，不得安装 / 删除真实 Windows 计划任务（除非申请中单独列明并获批）。
- 不得用真实账号执行会产生线上副作用且未列入申请的操作。

## 五、测试前快照（强制）

### 1. 范围与方式

1. 列出本次会读写的全部真实数据：`config/*.json`、`config/*.db`（含 `-wal` / `-shm`）、`download/` 中会被改动的产物、可能被安装 / 卸载的计划任务。
2. 普通 JSON / 文本文件：复制到 `_smoking/real-snapshots/<YYYY-MM-DD>_<任务名>/`，保留原时间戳，并记录 `大小 + 修改时间 + SHA-256`。
3. SQLite 数据库：优先用 sqlite3 备份 API 做一致性快照（应用运行中也可用），不要直接复制正在写入的库：

   ```python
   import sqlite3
   src = sqlite3.connect("file:config/collected.db?mode=ro", uri=True)
   dst = sqlite3.connect("_smoking/real-snapshots/<目录>/collected.db")
   src.backup(dst)
   ```

   同时记录每张表的行数。若只能裸复制，必须同时复制 `-wal` / `-shm`，并确认应用当时没有在写。
4. 计划任务：用 `schtasks /Query /TN <任务名> /XML` 导出 XML 到快照目录；测试后按 XML 恢复。
5. 生成 `manifest.txt`，逐行写 `相对路径 | 大小 | 修改时间 | SHA-256`，并打印在回复或报告里。
6. 快照目录位于 `_smoking/`（已忽略），不提交、不推送；不得把快照放回真实 `config/`。

### 2. 直播录制专项

直播录制的主播列表、备注、录制设置与监控状态都由 `config/live_record.json` 承载，另外还有房间缓存：

| 文件 | 内容 |
| --- | --- |
| `config/live_record.json` | 主播列表、备注、录制质量 / 内容 / 分段设置、上次录制 / 监控状态 |
| `config/live_rooms.json` | 账号 / 房间号解析缓存 |
| `config/bili_live.json`、`config/douyin_live.json` | 最近连接房间与平台设置 |
| `config/douyin_live_rooms.json` | 抖音连过的房间缓存 |

测试前必须整文件快照；测试后必须整文件还原。只要动过直播录制页面，默认这五个文件中涉及的都要核对，不能只还主播列表一项。

## 六、测试后还原（强制）

### 1. 顺序

1. 停止本次测试的所有操作，等待写入完成。
2. 若软件仍在运行且会把内存状态写回磁盘：请用户自己关闭软件后再还原；Agent 不得代为关闭或结束进程。用户不同意关闭时，如实说明「还原可能被运行中的实例覆盖」，不得声称已还原。
3. 按快照逐文件覆盖回原位置；数据库同时处理 `-wal` / `-shm`（删除快照中不存在的 `-wal/-shm`，或还原快照中的版本），避免旧库配新日志。
4. 校验：普通文件逐个比对 SHA-256 与 `manifest.txt`；JSON 业务数据解析后整体比较；数据库执行 `PRAGMA integrity_check` 并核对关键表行数。
5. 直播录制额外核对：主播数量、每条主播的房间号 / 平台 / 备注 / 顺序 / 启用状态、录制质量与内容设置、监控与录制状态，必须与测试前一致。
6. 更新当日报告，写明快照路径、覆盖文件、还原前后哈希、校验结果与残留风险。

### 2. 还原方式

- 一律「整文件回滚」：从快照复制回原位置，不靠手工编辑修补。
- **禁止**把「删掉测试主播」「把测试记录删掉」「重新加回用户的主播」当作还原；手工恢复会改变顺序、备注、时间戳和隐藏字段，这正是用户需要反复重新添加的原因。
- 如果确实无法整文件回滚（快照损坏、文件被占用），立即停止继续写入，保留现场与快照，列出未还原项、原因和备份位置，交由用户决定；不得反复覆盖或凭记忆重建。
- 还原失败或被运行中实例覆盖时，重新对比哈希确认实际状态，再次报告；不得用「应该没问题」结束任务。
- 若测试期间用户手动改过同一份数据：先确认用户的新改动，不要直接用旧快照覆盖；由用户决定保留哪份，并在报告中记录取舍。

### 3. Agent 中断时

测试中途被取消、上下文结束或任务切换：在离开前完成还原；确实来不及的，必须在当次回复中写明测试进行到哪一步、哪些文件已改、快照在哪里、需要用户执行什么。不能留下半改状态且不告知。

## 七、禁止行为清单

- 在项目真实 `config/` 里新建、修改、删除主播、账号、设置、数据库记录来「顺手测试」。
- 把真实 `cookies.json`、登录快照或真实主播列表复制进隔离副本。
- 测试完成后只删测试项，不还原快照。
- 用真实账号 / 真实数据跑会写线上状态的测试，即使只是「试一下」。
- 为了还原去关闭、重启用户正在使用的实例。
- 让隔离实例写入真实 `download/`、真实 `logs/` 或真实计划任务。
- 把测试数据、快照、日志提交进 Git 或写进发行包。
- 在报告里把「没还原」写成「已清理」「应该恢复」，或省略未还原项。

## 八、检查清单

- [ ] 本次测试是否默认跑在隔离副本（独立程序根、`config/`、`download/`、`logs/`、端口）？
- [ ] 启动前是否确认 `get_config_dir()` 指向副本，而不是项目真实 `config/`？
- [ ] 隔离副本是否没有复制真实 Cookie、真实主播列表和真实数据库？
- [ ] 需要接入用户实例或真实数据时，是否先提出申请并取得当次明确同意？申请是否写清范围、数据清单、快照、还原、风险与时长？
- [ ] 是否在真实环境写入前完成快照与哈希清单，快照位于 `_smoking/real-snapshots/` 且未提交？
- [ ] 直播录制是否覆盖 `live_record.json` 等实际涉及文件的快照与还原？
- [ ] 测试后是否按快照整文件还原并校验哈希 / 数据库完整性 / 主播列表逐项一致？
- [ ] 是否没有用「删除测试项」代替还原？
- [ ] 还原期间是否没有关闭 / 重启用户实例；需要关闭时是否由用户操作？
- [ ] 还原失败、被覆盖或未完成时，是否停止写入并如实报告快照位置与未还原项？
- [ ] 当日报告是否记录测试边界、快照路径、还原结果与残留风险，并完成本地提交？

## 九、与其他 skill 的关系

- [running-instance-guard](../running-instance-guard/SKILL.md)：运行中实例不得关闭 / 重启；本 skill 规定测试默认隔离与接入申请。
- [testing-quality-gates](../testing-quality-gates/SKILL.md)：测试层级、数据隔离与质量门禁；本 skill 补「真实环境接入与还原」。
- [test-cleanup](../test-cleanup/SKILL.md)：测试文件与缓存清理；快照属于恢复点，清理前必须确认，不随普通临时产物删除。
- [cookie-data-protection](../cookie-data-protection/SKILL.md) / [cookie-manager](../cookie-manager/SKILL.md)：真实凭据绝对保护；接入授权也不放宽。
- [data-lifecycle](../data-lifecycle/SKILL.md)：数据库备份、恢复与用户数据保留规则。
- [agent-coordination](../agent-coordination/SKILL.md)：并行测试时先确认谁在使用真实环境与快照目录。
